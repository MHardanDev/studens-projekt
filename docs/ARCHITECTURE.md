# المعمارية والقرارات

## قرار التقنية المبدئي

المشروع الحالي بدأ فارغاً عملياً عند المرحلة 0. في المرحلة 1 تم تأسيس موقع Django server-rendered، وليس تطبيق موبايل أو SPA.

- Django 5.2.17 LTS مع Django Templates. تم التحقق من صفحة تنزيل Django الرسمية في 2026-09-06؛ سلسلة 5.2 LTS مدعومة ممتداً حتى نيسان 2028.
- Python 3.13.5 في بيئة التطوير الحالية.
- PostgreSQL هو قاعدة البيانات المعتمدة عبر `DATABASE_URL` و`docker-compose.yml`. عند عدم توفر PostgreSQL محلياً يستخدم التطوير والاختبار SQLite كاحتياطي معلن فقط.
- HTML دلالي وCSS محلي وJavaScript صغير اختياري.
- RQ مع Redis مؤجل إلى مرحلة فحص الملفات، ولم يضف في المرحلة 1.
- تخزين PDF خاص وتسليم Nginx مؤجلان إلى مرحلة التنزيل، ولم يبدأ رفع الملفات.
- اختبارات Django وruff حالياً. Playwright وفحوص الوصول والأداء التفصيلية مؤجلة لمراحل الواجهة والـQA.

يجب إعادة التحقق من الإصدارات الرسمية والتوافق عند تنفيذ مرحلة التأسيس، وتثبيت الاعتماديات في lockfile. لا يضاف React أو Next.js أو إطار واجهات كامل للمشروع الجديد بلا مبرر وموافقة.

## قرارات المرحلة 1

- الإعدادات مفصولة إلى `config/settings/base.py` و`dev.py` و`test.py` و`production.py`.
- اللغة الافتراضية `ar` مع أساس تعدد لغات للغات `ar`, `en`, `de` ومسارات URL مترجمة بالبادئات.
- الاتجاه RTL للعربية وLTR للإنكليزية والألمانية، مع بقاء النصوص العربية الأصلية إلى أن تنشأ ملفات ترجمة فعلية.
- لا JavaScript في المسار العام الحالي؛ الصفحات تعمل بروابط ونموذج GET.
- أضيف Custom User minimal في `accounts.User` قبل أي نموذج مشروع آخر.
- الصفحة الرئيسية وصفحة التصفح تستخدمان بيانات تجريبية ثابتة وموسومة بوضوح، لا بيانات رسمية ولا ملفات منشورة.

## قرارات المرحلة 2

- أضيف تطبيق `catalog` للفهرس الدراسي والملفات الدراسية الأولية.
- الهيكل الدراسي مرن عبر `University`, `Faculty`, `Program`, `AcademicYearLevel`, `Term`, `Course`, و`CourseOffering`.
- لا توجد أرقام سنوات أو فصول أو مواد مثبتة في النماذج؛ أمر seed فقط ينشئ مثالاً تجريبياً محدداً بطلب مالك المشروع.
- `CourseOffering` هو رابط المادة بسياقها الدراسي: البرنامج، السنة، الفصل، والعام الأكاديمي الاختياري.
- أضيف `StudyDocument` كهوية ملف دراسي أولية بلا رفع PDF حقيقي وبلا تخزين ملفات.
- حالة `StudyDocument` الحالية أولية: `draft`, `pending`, `approved`, `rejected`, `archived`. عقد الفحص والمراجعة التفصيلي في المراحل اللاحقة سيبقى منفصلاً عن هذا الأساس.
- بيانات demo موسومة بـ`is_demo=True` وقابلة لإعادة الزرع عبر `seed_demo_catalog` دون تكرار.
- صفحة `/ar/browse/` تقرأ من قاعدة البيانات عبر علاقات Django، ولم تعد تعتمد على قوائم hardcoded داخل HTML أو view.

## قرارات المرحلة 3

- حسنت الواجهة العامة كتصميم عربي RTL أصلي موبايل أولاً، بلا خطوط خارجية وبلا صور ثقيلة وبلا JavaScript إلزامي.
- بقيت الواجهة server-rendered عبر Django Templates، ولم تضف SPA أو Bootstrap أو مكتبة CSS خارجية.
- أضيف مبدل لغة بروابط HTML عادية للغات `ar`, `en`, و`de`. العربية RTL، والإنكليزية والألمانية LTR.
- أضيف بحث GET في الرئيسية والتصفح، يبحث مبدئياً في أسماء المواد ورموزها وعناوين الملفات الدراسية المعتمدة.
- نتائج البحث تعرض من قاعدة البيانات، وتحافظ على نص البحث في الحقل، وتعرض حالة فارغة عربية عند عدم وجود نتائج.
- الصفحة الرئيسية تعرض أحدث الملفات التجريبية، الكليات المتاحة، ومواداً لا تملك ملفات بعد إن وجدت.
- صفحة التصفح تعرض الجامعة والكلية والبرنامج والسنوات والفصول والمواد والملفات الوصفية المرتبطة بالمادة من قاعدة البيانات.
- لم تبدأ صفحات تفاصيل المادة أو الملف كمسارات منفصلة بعد؛ ذلك مؤجل لمرحلة لاحقة من الفهرس العام.

## قرارات المرحلة 4

- بقيت الحسابات مبنية على Django auth و`accounts.User` المخصص من المرحلة 1؛ أضيف حقل `role` عبر migration جديد دون كسر migration الأولى.
- الأدوار الحالية: `Student`, `TrustedContributor`, `FacultyModerator`, و`SiteAdmin`.
- `TrustedContributor` لا يملك صلاحية نشر، و`can_publish_documents` يرجع `False` دائماً في هذه المرحلة.
- `FacultyModerator` لا يصبح `superuser` بمجرد قبول الدعوة.
- أضيفت `ContributorScope` و`ModeratorScope` لربط الدور بجامعة أو كلية أو برنامج أو مادة. لا يوجد نطاق مفتوح على الموقع كله افتراضياً.
- أضيفت `ContributorInvitation` بدعوة single-use، token عشوائي آمن، تاريخ انتهاء، وحالات `pending`, `accepted`, `revoked`, `expired`.
- قبول الدعوة يتم عبر صفحة server-rendered ويتطلب تسجيل الدخول، ويجب أن يطابق الحساب `invited_identifier` عبر اسم المستخدم أو البريد.
- لا ترسل الدعوات عبر بريد حقيقي في هذه المرحلة؛ رابط الدعوة يظهر في Django admin فقط.
- إدارة الدعوات والنطاقات في Django admin مقيدة بـ`superuser` أو مستخدم staff بدور `SiteAdmin`.
- منع الموافقة الذاتية موثق كقاعدة للمرحلة اللاحقة؛ لا توجد مراجعة ملفات أو نشر في المرحلة 4.

## قرارات المرحلة 5

- أضيف رفع PDF server-rendered عبر `catalog.upload_document` للمستخدمين بدور `TrustedContributor` فقط.
- الرفع لا يعمل إلا إذا كان للمساهم `ContributorScope` يطابق `CourseOffering` المختار عبر جامعة أو كلية أو برنامج أو مادة.
- الزائر يحول إلى تسجيل الدخول، و`Student` أو مساهم بلا نطاق يحصل على منع وصول.
- `StudyDocument` امتد بحقول التخزين الأولية: `uploaded_file`, `original_filename`, `file_size`, `uploaded_content_type`, و`scan_notes`.
- حالة الملف بعد الرفع هي `uploaded_pending_scan` وحالة الفحص `pending`.
- لا يوجد نشر تلقائي: الملف المرفوع لا يدخل نتائج التصفح العامة لأن العرض العام يقرأ فقط `approved + clean`.
- التخزين يستخدم `MEDIA_ROOT = private-media/`، وهو مجلد خاص مستثنى من Git ولا يقدمه Django كـstatic/public.
- الاسم الداخلي للملف يولد كـUUID داخل `study-documents/` ولا يستخدم اسم المستخدم أو اسم الملف الأصلي كمسار.
- التحقق الأولي يرفض غير PDF بناءً على الامتداد، نوع المحتوى المعلن، الحجم، وتوقيع البايتات `%PDF-`.
- حد الحجم المبدئي `MAX_UPLOAD_SIZE = 20 MiB`.
- لا يوجد رفع من URL خارجي، ولا توجد معاينة أو تنزيل للملف المرفوع في هذه المرحلة.
- لم يدمج ClamAV أو worker فعلياً بعد؛ النظام fail-closed لأن `scan_status=pending` لا يسمح بالنشر العام.

## قرارات المرحلة 6

- أضيف workflow مراجعة صريح لحالات الملفات: `uploaded_pending_scan`, `pending_review`, `approved`, `rejected`, و`archived`.
- لا ينتقل الملف إلى `pending_review` إلا إذا كانت `scan_status=clean`.
- لا يعتمد الملف إلا عبر `StudyDocument.approve()` من `FacultyModerator` أو `SiteAdmin` له `ModeratorScope` مطابق، ومع منع مراجعة الشخص لملفه.
- أضيفت صفحة مراجعة server-rendered على `/ar/moderation/documents/` تعرض فقط ملفات `pending_review + clean` داخل نطاق المشرف.
- الرفض يتم عبر POST ويتطلب سبباً مختصراً محفوظاً في `rejection_reason`.
- أضيف `DocumentVersion` كنسخة منشورة ثابتة؛ ظهور الملف العام يتطلب `approved + clean + published_version`.
- الموافقة تنشئ نسخة snapshot تشمل العنوان والوصف والمادة واسم الملف الداخلي والحجم وSHA-256 إن أمكن ومن رفع ومن راجع.
- لا يوجد تنزيل عام أو معاينة PDF في هذه المرحلة؛ النسخة المنشورة ميتاداتا فقط إلى أن تنفذ مرحلة التنزيل الآمن.
- أضيف `DocumentReport` للبلاغات على الملفات المنشورة فقط، مع صفحة بلاغ HTML عادية يمكن للزائر استخدامها.
- في Django admin أضيفت النسخ والبلاغات وفلاترها، وأضيف إجراء لإرسال الملفات النظيفة للمراجعة. منع تغيير `approved` يدوياً في admin مضبوط جزئياً عبر `clean()`، لكن workflow الصفحة هو المسار المعتمد للمراجعة.

## قرارات المرحلة 7

- أضيفت صفحة عامة لكل `StudyDocument` منشور على `/ar/documents/<id>/`، وتعرض metadata من `published_version` الثابتة لا من حقول مسودة قابلة للتغيير.
- توحد شرط الظهور العام في `catalog.publication.published_documents`: الحالة `approved`، والفحص `clean`، ووجود `published_version`.
- أضيف تنزيل خاص عبر Django على `/ar/documents/<id>/download/`. لا يقدم `MEDIA_ROOT` كـstatic ولا يقبل اسماً أو مساراً من المستخدم.
- يتحقق التنزيل مرة أخرى من شرط النشر، ومن أن الاسم الداخلي نسبي وتحت `study-documents/` وموجود في التخزين الخاص.
- يدعم التنزيل `GET`, `HEAD`, نطاق بايتات واحد، و`If-Range`. النطاق الصحيح يرجع `206` وغير الصالح يرجع `416` مع `Content-Range`.
- يرسل التنزيل `Content-Length`, `Accept-Ranges`, `ETag`, `Last-Modified`, `Content-Disposition`, و`Cache-Control: no-store`. يعتمد `ETag` على SHA-256 المحفوظ، مع validator ثابت مشتق من metadata عند غياب البصمة. تمنع ترويسة `no-store` تخزين الملفات المحكومة بالحجب في المتصفحات والبروكسي الوسيط.
- محتوى PDF يبث على دفعات 64 KiB ولا يحمل كاملاً في الذاكرة. دعم multi-range غير منفذ في هذه المرحلة.
- أضيف حقل `page_count` (اختياري null=True) في `DocumentVersion` فقط؛ ولا تستخدم خوارزميات تخمينية تقريبية ولا مكتبات جديدة، وفي حال تعذر استخراجه يظل `None` بأمان دون التأثير على الرفع أو النشر.
- تعرض صفحة الملف العامة حجم الملف ورقم الإصدار المنشور وعدد الصفحات إن توفر بأمان، بالإضافة لزر التنزيل وزر البلاغ.
- أضيف وضع توفير بيانات بلا JavaScript عبر POST محمي بـCSRF وكوكي `HttpOnly`, `SameSite=Lax` غير حساس لمدة 30 يوماً. لا توجد معاينة تلقائية أصلاً في المسار العام.
- يحفظ آخر ملف أو صفحة تصفح أو بحث كمسار داخلي محدود في كوكي `HttpOnly` لمدة 30 يوماً. لا تحفظ أسماء مستخدمين أو توكنات أو بيانات جلسة، وترفض الروابط الخارجية والقيم غير المطابقة لمسارات عامة معروفة.
- ملفات demo الوصفية تبقى قابلة لفتح صفحة metadata، لكن لا يظهر لها زر تنزيل لأنها لا تحتوي PDF فعلياً.
- توثيق معمارية Nginx المستقبلية للإنتاج:
  - في بيئة الإنتاج، يتحقق Django من الصلاحيات وحالة النشر لكل طلب، ثم يرسل ترويسة `X-Accel-Redirect` إلى Nginx مع ترويسات `Cache-Control: no-store` و`Content-Disposition` دون إرسال جسم الملف عبر بايثون.
  - يتولى Nginx قراءة الملف من المجلد الداخلي وتسليمه بكفاءة عالية عبر `sendfile` وإدارة طلبات `Range` و`If-Range` مباشرة من نواة النظام دون استهلاك ذاكرة خادم التطبيق.
  - تكوين Nginx المطلوب مستقبلاً:
    ```nginx
    location /internal-media/ {
        internal;
        alias /path/to/private-media/;
        sendfile on;
        tcp_nopush on;
        add_header X-Content-Type-Options "nosniff" always;
        add_header Cache-Control "no-store" always;
    }
    ```
  - يبقى البث عبر `StreamingHttpResponse` في Django هو البديل الخادمي الفعال في بيئة التطوير والاختبار المحلي.

## حدود الوحدات المتوقعة

- الحسابات والصلاحيات: المستخدمون، الأدوار، النطاقات، الدعوات، جلسات Django، CSRF. MFA للإدارة والإشراف مؤجل لمرحلة لاحقة مناسبة.
- الفهرس الدراسي: الجامعات، الكليات، البرامج، الخطط، السنوات، الفصول، المواد، وطرح المادة ضمن خطة وفصل.
- المحتوى والملفات: `StudyDocument` يدعم الرفع الخاص الأولي وحالة الفحص. الإصدارات غير القابلة للاستبدال، الفحص الفعلي، والمعاينات مؤجلة لمراحلها.
- المراجعة والإشراف: صفحة مراجعة ونطاقات وبلاغات ونسخ منشورة ثابتة. سجل إجراءات تفصيلي والحجب الكامل مؤجلان لمراحل لاحقة.
- تجربة الطالب: البحث، التصفح، صفحة الملف والتنزيل المتدفق، وضع توفير البيانات، واستئناف آخر مسار. المفضلة وطلبات المحتوى مؤجلتان.
- التشغيل والثقة: صفحات السياسات، القياس المحدود، الإعلانات المعطلة، النسخ الاحتياطي، runbook.

## عقد حالات الملفات

حالة المراجعة للإصدار منفصلة عن حالة الفحص وعن ظهور الوثيقة:

- مسودة.
- معالجة.
- انتظار مراجعة.
- مطلوب تعديل.
- مرفوض.
- معتمد.

حالة الفحص منفصلة:

- بانتظار الفحص.
- نجح الفحص.
- فشل الفحص.

شروط الظهور العام:

- وجود إصدار منشور معتمد عبر `DocumentVersion`.
- نجاح فحص الوثيقة المرتبطة.
- اكتمال ومقبولية أساس الحقوق.
- عدم وجود حجب على الوثيقة أو الإصدار.

الحجب يمنع الظهور والتحميل والمعاينة والروابط البديلة، ولا يلغيه إصدار جديد إلا بعد معالجة السبب ومراجعة جديدة.

## عقد الصلاحيات

- الزائر يصل فقط إلى المنشور وغير المحجوب.
- الطالب يدير بياناته ومفضلاته وطلباته فقط.
- المساهم يرفع ويقترح تحديثات ضمن نطاقه فقط، ولا ينشر بنفسه.
- المشرف يراجع ضمن نطاقه فقط، ولا يراجع نسخة رفعها بنفسه.
- المدير يدير النطاقات والمستخدمين، لكنه لا يحول فشل الفحص أو الحقوق إلى نشر صالح.

كل عملية تغيير حالة يجب أن تكون POST محمية بـCSRF، وأن يعاد التحقق منها على الخادم حتى لو كان المستخدم يحتفظ بتبويب قديم.

في المرحلة 4، الخروج وقبول الدعوة عمليتان POST محميتان بـCSRF. صفحات القراءة والتصفح والبحث لا تتطلب حساباً.

## قرارات محتوى وحقوق

- لا نسخ لشعار أو نصوص أو تصميم مميز أو ملفات من Studydrive أو Studocu أو غيرهما.
- المراجع الخارجية تستخدم لفهم الاحتياج والأنماط العامة فقط.
- شراء ملخص من مكتبة أو إيجاده على قناة عامة لا يكفي إذناً للنشر.
- أدلة الإذن تحفظ في مساحة خاصة ولا تعرض للجمهور.
- النصوص القانونية والسياسات مسودات تحتاج مراجعة مالك المشروع ومختص قبل الإطلاق.

## حدود التشغيل

- تطوير وبناء المشروع محلياً والاستضافة الدائمة للإنتاج قراران منفصلان.
- إن كانت منصة النشر صفحات ثابتة فقط، يجب حسم مكان تشغيل الخادم قبل اختيار التقنية النهائية.
- لا خدمات مدفوعة أو حسابات خارجية أو نشر عام أو رسائل حقيقية دون موافقة صريحة.
