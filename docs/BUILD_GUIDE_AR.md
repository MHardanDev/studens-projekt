# دليل بناء منصة جامعية سورية: خطة ومراحل التنفيذ

تاريخ إعداد الدليل ومراجعة المراجع: 6 أيلول 2026.

هذا دليل تنفيذ، وليس موقعاً منفذاً أو ضماناً لغياب الأخطاء. المراحل الواردة في هذا الدليل تمثل تسلسلاً معيارياً لتنفيذ المتطلبات وتحويلها إلى كود برمجي يعمل واختبارات موثقة داخل مشروع واحد.

## 1. ما المشروع الذي نبنيه؟

منصة عربية مستقلة يتساعد فيها الطلاب عبر ملخصات وملاحظات دراسية يملكونها أو لديهم إذن بنشرها. البحث والقراءة والتنزيل مجانيان، ولا يتطلبان حساباً. الحساب مطلوب للمفضلة وطلبات المحتوى والمساهمة. رفع الملفات محصور بمساهمين يعتمدهم مدير المنصة، ولا يتحول الرفع إلى نشر تلقائي.

الطالب قد يستخدم هاتف شاومي أو سامسونغ قديماً، ذاكرة محدودة واتصالاً متقطعاً. لذلك نبني موقعاً خفيفاً يعمل من المتصفح، وليس تطبيقاً يحتاج التنزيل من المتجر. اختلاف إصدار المتصفح والذاكرة أهم من اسم الشركة المصنعة.

نبدأ بمحتوى سنة واحدة وفصل واحد ضمن كلية واحدة. لكن قاعدة البيانات تستوعب جامعات وكليات وخططاً دراسية متعددة. مثال أربع سنوات وفصلين و12 مادة في الفصل وصفٌ لحالة محتملة، وليس رقماً ثابتاً في البرمجة أو إثباتاً للخطة الرسمية.

الربح المحتمل من إعلانات محدودة يأتي لاحقاً. لا نربط استمرار مجانية الملفات بقبول AdSense أو بوعد دخل معين.

## 3. التقنية المقترحة وحدود النسخة الأولى

هذا الاختيار للمشروع الجديد فقط. إذا كان لديك مشروع قائم صالح، يُفحص وتُكيّف المراحل معه قبل اقتراح أي إعادة بناء.

الخطة تحتاج بيئة تشغيل تدعم خادم Python وقاعدة بيانات ومهام خلفية، أو خدمات خارجية مكافئة متصلة فعلياً. إذا كانت منصة النشر المتاحة تدعم صفحات ثابتة فقط، يجب حسم مكان تشغيل الخادم قبل اختيار التقنية؛ لا نستبدل الحسابات والتخزين والمراجعة بمحاكاة في المتصفح. بناء وتطوير المشروع محلياً واستضافته الدائمة قراران منفصلان.

| الجزء | الاختيار المبدئي | السبب |
|---|---|---|
| الخادم والصفحات | Django 5.2 LTS بأحدث تحديث أمني متاح عند التنفيذ، مع Django Templates | صفحات مكتملة من الخادم، ونظام حسابات وإدارة جاهز للبناء عليه |
| الواجهة | HTML دلالي، CSS محلي، JavaScript صغير اختياري | تخفيف التنزيل والعمل على معالج الهاتف |
| البيانات | PostgreSQL للتطوير والاختبارات والإنتاج | تقليل اختلاف السلوك بين البيئات |
| المهام الخلفية | RQ مع Redis بإصدارات متوافقة ومثبتة | فصل فحص الملفات ومعالجتها عن طلبات المستخدم |
| ملفات PDF | تخزين خاص خارج المجلد العام؛ Nginx يسلّم الملف بعد تحقق Django | تنزيل فعال مع منع الوصول المباشر للمسودات |
| التشغيل | تطبيق واحد معياري، Gunicorn وNginx، وDocker Compose عند توفره | تشغيل مفهوم بلا خدمات مصغرة أو Kubernetes |
| الاختبارات | pytest وpytest-django وPlaywright وأداة فحص وصول وأداء | اختبار السلوك الفعلي، لا الصور فقط |

دعم Django 5.2 LTS الممتد معلن حتى نيسان 2028؛ يجب إعادة التحقق من الإصدارات والتوافق عند التنفيذ. اختيار Django هنا قرار هندسي للمشروع، وليس شرطاً لعمل المواقع على الهواتف القديمة. [إصدارات Django المدعومة](https://www.djangoproject.com/download/). وتدعم RQ تنفيذ المهام عبر workers؛ نستخدمها لهذا الغرض فقط. [توثيق RQ](https://python-rq.org/docs/).

التخزين الخاص على خادم واحد يكفي كبداية تشغيلية محدودة، لكنه نقطة فشل واحدة؛ النسخة الاحتياطية الخارجية إلزامية. لا يلزم إضافة تخزين كائنات أساسي أو CDN من اليوم الأول. نترك استخدام واجهة التخزين القياسية ممكناً للانتقال لاحقاً، بلا بناء نظام تخزين عام معقد.

خارج النسخة الأولى: تطبيق Android، دردشة، شبكة اجتماعية، تعليقات مفتوحة، فيديو، OCR شامل، مساعد AI، بيع ملفات، اشتراكات، نظام نقاط قابل للصرف، وشراكات مكتبات آلية. هذه إضافات لاحقة تحتاج دليلاً على الحاجة.

## 4. الصفحات ورحلة الطالب

| الصفحة | الوظيفة الأساسية |
|---|---|
| الرئيسية | بحث واختيار الجامعة والكلية ثم السنة والفصل، مع مواد فعلية منشورة |
| الكلية والخطة | السنوات والفصول المتاحة، دون افتراض أعداد ثابتة |
| المادة | وصف قصير أصلي، الفصل والعام، الملفات المنشورة وفرزها |
| نتائج البحث | نتائج عربية وفلاتر وروابط صفحات قابلة للمشاركة |
| الملف | العنوان والمصدر والإصدار والحجم والصفحات والتاريخ، تنزيل ومعاينة بطلب المستخدم |
| مكتبتي | مفضلة وروابط مواد يتابعها صاحب الحساب؛ ليست دليلاً أن PDF محفوظ على هاتفه |
| طلب مادة | طلب ملف ناقص مرتبط بمادة وفصل وعام، مع منع التكرار |
| المساهمة | طلب اعتماد، ثم رفع للمساهم المعتمد وتتبع حالة المراجعة |
| الإشراف | مراجعة الإصدارات والبلاغات وطلبات المواد ضمن نطاق الصلاحية |
| الإدارة | الجامعات والخطط والمستخدمون والصلاحيات ومؤشرات التغطية والتشغيل |
| صفحات الثقة | عن المبادرة، التواصل، الخصوصية، الاستخدام، حقوق المحتوى والاعتراض |

الرحلة الأساسية: يفتح الطالب الموقع، يختار مادته أو يبحث عنها، يرى الملف المناسب وحجمه، ثم ينزله. لا نافذة تسجيل إجبارية ولا إعلان يفصل بينه وبين التنزيل.

## 5. متطلبات الهواتف القديمة والإنترنت الضعيف

الأساس هو التحسين التدريجي: يبقى المحتوى والوظائف الضرورية متاحين، وتضاف ميزات للمتصفحات التي تدعمها. [شرح MDN](https://developer.mozilla.org/en-US/docs/Glossary/Progressive_Enhancement).

هذه ميزانيات هندسية أولية نقيسها ونراجعها، وليست أرقاماً من مواقع المنافسين أو وعداً لجميع الأجهزة:

| البند | معيار القبول المبدئي |
|---|---|
| العرض | 320 و360 و390 و412 و768 و1280 بكسل، بلا تمرير أفقي للصفحة |
| القراءة | خط أساسي 16px، تباعد أسطر مريح، تكبير نص واختبار RTL |
| اللمس | مساحة تفاعل مقترحة لا تقل عن 44×44 CSS px للعناصر الأساسية |
| أول تحميل | HTML وCSS وJS والأيقونات معاً لا تتجاوز 150 KiB مضغوطة للصفحات العامة الأساسية |
| JavaScript | لا يتجاوز 35 KiB مضغوطاً في المسار الأولي؛ الوظائف الأساسية لا تعتمد عليه |
| CSS | لا يتجاوز 30 KiB مضغوطاً للمسار الأولي؛ لا خط ويب خارجي |
| الشبكة | هدف لا يتجاوز 15 طلباً أولياً؛ صفر طلبات PDF أو معاينات أو إعلانات تلقائية عند تعطيلها |
| ملف PDF | حد أولي قابل للضبط 20 MiB للرفع، مع عرض الحجم الفعلي وليس تقديراً |
| المعاينة | أول ثلاث صفحات كحد أولي، صورة واحدة عند الطلب في كل مرة، مع تنزيل كامل منفصل |
| الاستئناف | تحقق من HTTP Range وهوية إصدار ثابتة؛ سلوك الاستئناف النهائي يعتمد أيضاً على المتصفح ومدير التنزيل |

أحجام النقل السابقة تستثني الملف والمعاينة اللذين طلبهما الطالب صراحة. بعد تفعيل الإعلانات لا نخبئ تكلفتها: نقيس وزن الصفحة الكامل مجدداً، ولا ننسب نتيجة الصفحة بلا إعلانات إلى الصفحة التي تعرضها.

نستخدم نموذجين اختباريين للشبكة: الأول 1.6 Mbps تنزيل و750 Kbps رفع وRTT يساوي 150ms مع إبطاء CPU بمقدار 4×؛ والثاني 400 Kbps تنزيل و200 Kbps رفع وRTT يساوي 400ms مع إبطاء CPU بمقدار 6×. تُوثّق أداة المحاكاة ومعنى إعداداتها. هذه نماذج اختبار، وليست قياساً لسرعة الإنترنت في سوريا.

في النموذج الأول نستهدف LCP مختبرياً لا يتجاوز 4 ثوانٍ للصفحات الأساسية، مع إظهار النتائج الفعلية والفشل بوضوح. أما أهداف Core Web Vitals الميدانية فهي LCP حتى 2.5 ثانية وINP حتى 200ms وCLS حتى 0.1 عند المئين 75، عندما تتوفر بيانات كافية. لا نخلط قياس المختبر بالزيارات الحقيقية أو ندعي قياس INP لمستخدمين لم يزوروا الموقع. [مرجع Web Vitals](https://web.dev/articles/vitals).

تُختبر أجهزة حقيقية مبدئياً بذاكرة 2GB ونظام Android 7 أو 8 أو 9 إن توفرت، بالإضافة إلى هاتف أحدث. يسجل المختبر الطراز والنظام والمتصفح وإصداره. نستهدف عمل الأساس في المتصفحات القديمة الممكن اختبارها، ونوصي بآخر تحديث متاح؛ لا نستطيع جعل نظام مهمل أمنياً آمناً بتعديل الموقع. Playwright على شاشة ضيقة لا يثبت توافق شاومي قديم أو محدودية ذاكرته.

## 6. طريقة استخدام الأوامر دون تكرار

1. اعمل داخل مشروع واحد، واجعل هذا الدليل متاحاً كمرجع رئيسي ضمن ملفات المشروع.
2. أرسل الأمر 0 أولاً ليحفظ الاتفاق والمتطلبات. بعده أرسل الأمر 1.
3. أكمل الأوامر 2 إلى 12 بالترتيب، أمراً واحداً في كل رسالة. لا تطلب بناء المراحل كلها دفعة واحدة.
4. في نهاية كل مرحلة راجع رابط التشغيل والاختبارات والعوائق. لا تنتقل لمرحلة تعتمد على جزء فاشل.
5. عند فتح محادثة جديدة استخدم أمر الاستئناف الموجود في آخر الدليل. لا تعِد التأسيس أو تكتب وصفاً مختلفاً للفكرة.

لا يوجد أمر يضمن صفراً من الأخطاء. الذي يقلل الأخطاء هو توحيد المتطلبات، وصغر المراحل، واختبارات حقيقية، وعدم تغيير التقنية والتصميم كل مرة.

## الأمر 0: عقد العمل وذاكرة المشروع

أرسله مرة واحدة. لا يبدأ بناء الموقع في هذه المرحلة.

```text
أريد تنفيذ منصة جامعية عربية للطلاب في سوريا وفق دليل docs/BUILD_GUIDE_AR.md المعتمد. اقرأ الدليل كاملاً، ثم نفذ المرحلة 0 فقط.

افحص المشروع الموجود وتعليماته وحالة Git قبل أي تعديل. إذا لم يتوفر الدليل لديك، اطلبه مني ولا تتخيل محتواه. لا تعِد إنشاء مشروع قائم أو تستبدل تقنيته دون ضرورة موثقة وموافقتي.

احفظ المرجع الكامل باسم docs/BUILD_GUIDE_AR.md إذا لم يكن محفوظاً في المشروع، ولا تنشئ نسخة ثانية منه إن كانت هناك نسخة معتمدة.

أنشئ أو حدّث الوثائق التالية مع الحفاظ على التعليمات الموجودة:
- AGENTS.md: قواعد مختصرة ثابتة للعمل وروابط وثائق المشروع.
- docs/PRODUCT.md: هدف المنصة، نطاق النسخة الأولى، الصفحات، الأدوار، ومتطلبات القبول بمعرّفات ثابتة مثل REQ-001.
- docs/ARCHITECTURE.md: التقنية المختارة، قراراتها، حدود الوحدات، وعقد حالات الملفات والصلاحيات.
- docs/PROGRESS.md: سجل مراحل 0 إلى 12، المكتمل فعلياً، الاختبارات، العوائق، والخطوة التالية.
- docs/OPEN_QUESTIONS.md: ما يحتاج قرار مالك المشروع قبل الإطلاق، دون تعطيل التطوير بقرارات شكلية.

القواعد الثابتة:
1. البحث والقراءة والتنزيل مجانيان للزائر. الحساب ليس شرطاً للوصول للمحتوى المنشور.
2. الجمهور هو الهواتف القديمة والاتصال الضعيف. الوظائف الأساسية تعمل بروابط ونماذج HTML دون JavaScript.
3. واجهة عربية RTL أصلية؛ لا نسخ لشعار أو نصوص أو تصميم مميز أو ملفات منافس.
4. الرفع للمساهم المعتمد فقط. الرفع والتعديل لا يعنيان النشر. الصلاحيات تتحقق على الخادم لكل كائن وعملية.
5. لا ينشر ملف قبل اكتمال فحصه ومراجعة حقوقه ومحتواه التنظيمية. اعتماد المساهم ليس شهادة صحة علمية.
6. المحتوى والتخزين الخاص والحسابات حقيقية. لا تستخدم localStorage كقاعدة بيانات أو نظام صلاحيات، ولا تعرض نجاحاً وهمياً.
7. لا خدمات مدفوعة أو نشر عام أو رسائل لأشخاص حقيقيين أو إعلانات مفعلة دون موافقتي وتهيئة فعلية.
8. استخدم المكتبات القياسية الموثوقة والتقنية القائمة. تحقق من الإصدارات وثبتها في lockfile؛ لا تغيّر الحزمة كل مرحلة.
9. نفذ المرحلة المطلوبة فقط. أعد استخدام الموجود، واترك التعديلات غير المتعلقة بالمهمة كما هي.
10. قبل كل مرحلة اقرأ AGENTS.md وPRODUCT.md وARCHITECTURE.md وPROGRESS.md، وافحص الكود المرتبط بها.
11. لا تحذف اختباراً أو تخفف معيار قبول فقط للحصول على نجاح. أصلح السبب الجذري وأضف اختبار انحدار.
12. ميّز البيانات التجريبية، ولا تعرض أرقام استخدام أو تقييمات أو كليات أو خطط رسمية مختلقة.

صيغة تسليم كل مرحلة: ما تغير، كيف أجرّبه، أوامر الاختبار ونتائجها الفعلية، ما لم يُختبر ولماذا، والخطوة التالية. حدّث PROGRESS تدريجياً. لا تقل "جاهز للإنتاج" إذا بقيت عوائق إطلاق.

في هذه المرحلة سلّمني ملخص فهمك والمتطلبات والافتراضات والوثائق فقط، ثم توقف.
```

## الأمر 1: تأسيس تطبيق يعمل

```text
نفذ المرحلة 1 وفق العقد المحفوظ، بعد قراءة وثائق المشروع والكود الحالي.

للمشروع الجديد: استخدم Django 5.2 LTS بأحدث إصدار أمني متوافق، Python مدعوماً ومتوافقاً، PostgreSQL، Django Templates، وCSS وJavaScript محليين صغيرين. افصل وحدات الحسابات والفهرس والمحتوى والإشراف حيث يبرر نطاقها ذلك، دون خدمات مصغرة أو API منفصل بلا حاجة.

تحقق من التوافق عبر الوثائق الرسمية وثبت الاعتماديات. استخدم مدير حزم واحداً، وlockfile، وفصل إعدادات التطوير والاختبار والإنتاج. لا تضف React أو Next.js أو مكتبة واجهات كاملة للمشروع الجديد.

أنشئ Custom User minimal من البداية قبل أول migrations للحسابات. استخدم مصادقة Django ولا تكتب تشفيراً أو إدارة جلسات من الصفر. أكمل تجربة الحساب والصلاحيات في المرحلة 4.

جهز .env.example بقيم غير سرية، واستثناء الأسرار والرفع والنسخ الاحتياطية من Git. لا تنشئ كلمة مرور إدارية ثابتة ولا تنسخ إعدادات إنتاج إلى الاختبارات.

أضف Docker Compose لتشغيل PostgreSQL محلياً مع volumes دائمة، وطريقة تشغيل واضحة. إن لم تتوفر Docker فوثق وشغّل البديل المحلي الممكن؛ لا تدّع أن خدمة غير موجودة تعمل.

أنشئ صفحة رئيسية عربية هي بداية الأداة: عنوان مؤقت قابل للتغيير من إعداد واحد، بحث وهيكل اختيار الدراسة وحالة فارغة صادقة. لا تصمم صفحة تسويقية أو إحصاءات وهمية. لا تضف أزراراً تبدو فعالة بلا وظيفة؛ وصل الوظائف في مراحلها.

جهز static files، وقالباً عاماً، وصفحات 403 و404 و500، وhealth endpoint محدود المعلومات. افصل فحص حياة العملية عن جاهزية قاعدة البيانات. جهز pytest وlint وCI أساسياً متوافقاً مع بيئة المشروع، دون نشر تلقائي للإنتاج.

معيار القبول: تشغيل المشروع من إعداد نظيف، اتصال فعلي بـPostgreSQL، migrations سليمة، تحميل الرئيسية والملفات الثابتة، اختبار smoke يمر، وتوثيق الأوامر والإصدارات. شغّل الخادم محلياً وأعطني الرابط إن أمكن؛ لا تستخدم منفذاً مشغولاً.
```

## الأمر 2: نموذج الدراسة والملفات دون أرقام جامدة

```text
نفذ المرحلة 2، وأعد استخدام ما أُنشئ في المرحلة 1.

صمم نموذجاً يدعم University، Faculty، Program عند الحاجة، CurriculumPlan، StudyLevel، Term، Course، وCourseOffering. ميّز السنة الدراسية داخل الفرع عن العام الأكاديمي مثل 2026/2027، وميّز المادة عن طرحها ضمن خطة وفصل معينين. لا تثبت أربع سنوات أو فصلين أو 12 مادة في الكود.

معيار القبول: اختبارات العلاقات والقيود والحالات، عدم تضاعف seed، وعدم ظهور ملف غير معتمد في استعلامات الجمهور. اربط المتطلبات بالاختبارات، ووثق قرارات النموذج قبل الانتقال.
```

## الأمر 3: تصميم عربي أصلي وفهرس قابل للاستخدام

```text

راجع الصفحات العامة لـStudydrive وStudocu كمرجع للوظائف فقط إن كانت متاحة. دوّن في ARCHITECTURE روابط ما راجعته والأفكار التي استخلصتها وما ستصممه بصورة مستقلة. لا تسحب ملفات أو صوراً أو نصوصاً أو CSS منها، ولا تتجاوز تسجيل دخول أو شروط وصول. إذا تعذرت المراجعة استخدم المراجع الموثقة ولا تدّع أنك رأيت صفحات لم تفتحها.

البحث نموذج GET يعمل دون JavaScript، وفلاتره محفوظة في URL. ابحث في عنوان المادة وأسمائها البديلة وعنوان الملف ووصفه فقط في البداية. طبّع التشكيل والتطويل وأشكال الألف للبحث مع حفظ الأصل، واختبر أمثلة مثل "إحصاء" و"احصاء". لا تدمج حروفاً مختلفة دلالياً دون اختبار ولا تضف محرك بحث خارجي حالياً.

معيار القبول: رحلة بحث من الرئيسية حتى تفاصيل ملف منشور ببيانات تجريبية، تعمل مع JavaScript وبدونه. لقطات Playwright بعرض 320 و360 و390 و768 و1280، بلا قص أو تداخل. اختبارات تمنع تسرب المسودات عبر البحث والفلاتر والروابط المباشرة.
```

## الأمر 4: الحسابات ودعوة المساهمين والصلاحيات

تؤكد إرشادات OWASP ضرورة التحقق من التفويض في الطلبات وعدم الاكتفاء بعناصر الواجهة. سنختبر نطاق الكلية والوثيقة أيضاً، لا اسم الدور وحده. [مرجع التفويض](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

```text
نفذ المرحلة 4 باستخدام نظام Django للحسابات والجلسات، أو النظام الموثوق القائم في المشروع.

الأدوار: زائر يتصفح وينزل المنشور؛ طالب لديه مفضلة وطلبات؛ مساهم معتمد يرفع ويقدم تحديثات لملفاته ضمن مواد مسموحة؛ مشرف كلية يراجع ضمن نطاقه؛ مدير يدير المستخدمين والنطاقات. لا تساوِ بين دور المشرف وsuperuser.

نفذ تسجيل حساب ببريد وكلمة مرور واسم عرض، تسجيل دخول وخروج POST، تحقق بريد، واستعادة كلمة المرور بروابط قصيرة العمر وحيدة الاستخدام. القراءة والتنزيل يظلان متاحين دون تحقق بريد أو حساب. لا تجعل Google login أو SMS أو مكتبة خارجية ثقيلة شرطاً للوصول.

استخدم جلسات آمنة في cookies وليس tokens في localStorage، وحماية CSRF لكل تغيير حالة. طبّق إعدادات كلمات المرور وحماية محاولات الدخول والاستعادة دون تسريب وجود البريد. اجعل رسائل النماذج عربية، ولا تكشف البريد أو الاسم الحقيقي علناً تلقائياً.

أضف طلب اعتماد مساهم من الطالب، ولوحة للمدير لقبول الطلب أو دعوة مستخدم وتحديد الجامعة والكلية والمواد المسموحة. الدعوة مرتبطة بالمستلم، محدودة العمر، قابلة للإلغاء، ولا تقبل مرتين. يمنح الخادم الدور من الدعوة الصالحة ولا يثق بدور يرسله المتصفح.

اسحب الصلاحية فوراً عند إلغائها، بما يشمل محاولات الرفع والمراجعة المباشرة من تبويب قديم. لا تجعل دوراً عالمياً يمنح وصولاً لكل الكليات. أمن كل واجهات العرض والتحميل والعمليات بالجملة وأدلة الحقوق الخاصة. لا تعتمد على UUID كحماية.

طبق MFA للمدير والمشرفين بمكتبة موثوقة متوافقة مع Django، مع مسار استرداد آمن، وليس WebAuthn إجبارياً على الطلاب. تحقق من المصادقة الثنائية لكل مسارات الإدارة الحساسة لا شاشة دخول واحدة فقط. وثق الحزمة المختارة وراجع توثيقها الرسمي.

استخدم خدمة بريد محلية للاختبار، ولا ترسل رسائل حقيقية بلا إعداد واعتماد. وثق تعذر البريد كعائق قبل الإطلاق، لا كنجاح. لا تطلب صور هويات أو بطاقة جامعة لهذا الإصدار.

معيار القبول: جدول اختبارات إيجابية وسلبية لكل دور ونطاق؛ طالب يحاول الرفع، مساهم يعدل ملف غيره، مشرف يراجع كلية أخرى، دعوة مستعملة أو ملغاة، وسحب صلاحية لحساب مفتوح. اختبر CSRF وعدم تجاوز MFA وتغيير بيانات الحساب بصورة آمنة. مسار طلب حذف الحساب يُستكمل في المرحلة 9 مع سياسة الاحتفاظ.
```

## الأمر 5: رفع الملفات وفحصها بأمان

توصي OWASP بدفاعات متعددة للرفع، منها تقييد الأنواع والأحجام والتخزين والفحص، ولا يكفي اسم الملف أو نوعه المعلن. [رفع الملفات](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html). أداة الفحص لا تثبت أن المحتوى صحيح علمياً أو خالٍ من كل تهديد. [توثيق ClamAV](https://docs.clamav.net/manual/Usage/Scanning.html).

```text
نفذ المرحلة 5: رفع PDF للمساهم المعتمد دون نشر تلقائي.

نموذج الرفع: طرح المادة، نوع المحتوى، العنوان والوصف، العام والفصل، اسم المؤلف وطريقة عرضه، مصدر المحتوى وحقوق نشره، ثم PDF. احفظ الميتاداتا الصحيحة عند خطأ التحقق. لا تطلب من الهاتف تحويل الصور إلى PDF أو تنفيذ OCR داخل المتصفح.

اقبل PDF فقط، بحد أولي 20 MiB قابل للضبط وحد صفحات مبدئي 200. ارفض الملفات المشفرة بكلمة مرور أو التالفة أو ذات محتوى نشط أو مرفقات مضمنة بحسب قواعد فحص موثقة. تحقق من الحجم على مستوى البروكسي والتطبيق ونوع البايتات وفاحص PDF، لا MIME أو الامتداد وحدهما.

خزن الملفات أولاً في quarantine خاص غير قابل للوصول العام، بأسماء داخلية عشوائية. لا تستخدم اسم المستخدم كمسار ولا تسمح باستبدال ملف قائم. عالج الرفع بتدفق/ملف مؤقت وحدود ذاكرة ومساحة قرص، لا قراءة كل الملف إلى RAM.

أضف RQ وRedis عند هذه المرحلة فقط، مع worker حقيقي. نفذ فحص مكافحة البرمجيات الضارة بقاعدة توقيعات محدثة، وفحص PDF واستخراج عدد الصفحات والبصمة والحجم، وتوليد معاينة محدودة. لا تفتح الملف الخام في متصفح المشرف قبل اجتياز الفحص.

معالجة PDF تكون داخل sandbox مستقل بحدود وقت وذاكرة وعدد بكسلات، دون شبكة أو أسرار. worker يتولى جلب الملف وحفظ النتائج خارج بيئة التحليل المعزولة. استخدم أدوات ومكتبات موثوقة ومحدثة، وراجع تراخيص المحول وعارض PDF قبل اختيارهما.

إذا توقف الفحص أو تجاوز الحدود أو تعذر تحديثه وفق السياسة، يبقى الملف غير قابل للنشر. لا تحول نتيجة مجهولة إلى نجاح. أظهر حالة مفهومة للمساهم وخطأ تشغيل مفصلاً محمياً للمشرف.

اجعل المهام قابلة لإعادة المحاولة دون تكرار الإصدارات أو النشر. اعتمد سجلاً دائماً للمهمة في قاعدة البيانات واسترجاعاً للمهام المعلقة إذا فشل enqueue بعد الحفظ أو فقد Redis بياناته؛ لا تعتمد على الطابور وحده لحقيقة الحالة.

يدعم نموذج HTML رفعاً عادياً دون JavaScript. التحسين الاختياري يستخدم تقدم رفع حقيقياً وإلغاءً وإعادة محاولة، مع حماية من الإرسال المكرر. بعد انقطاع الاتصال احفظ البيانات النصية الآمنة، لكن لا تدع أن الملف نفسه سيعود إلى حقل الاختيار تلقائياً؛ قد يلزم اختياره مجدداً.

في النسخة الأولى الرفع المتقطع يعاد من البداية، ولا تعرض كلمة "استئناف" كميزة لم تنفذ. الاستئناف الجزئي للرفع مؤجل؛ إن أثبتت التجربة الحاجة إليه فله مرحلة منفصلة باستخدام بروتوكول ومكتبة موثوقين.

افحص البصمة لكشف التكرار دون كشف وجود ملفات خاصة لغير أصحابها. وفر تنظيفاً مجدولاً للرفع غير المكتمل والملفات المؤقتة، مع تجنب حذف الملفات المرجعية أو الأدلة المحتفظ بها.

معيار القبول: PDF صالح، امتداد مزيف، تجاوز الحجم، PDF تالف أو مشفر، تعطل الفاحص، انتهاء مهلة المعالجة، إرسال مكرر، انقطاع رفع، ووصول مباشر إلى quarantine. استخدم عينات اختبار آمنة؛ لا تنزل برمجيات ضارة حقيقية. لا ينجح نشر أي ملف في هذه المرحلة تلقائياً.
```

## الأمر 6: المراجعة والنشر والإصدارات والبلاغات

```text
نفذ المرحلة 6: لوحة مراجعة عملية ضمن نطاق الكلية، مع قواعد انتقال حالات تنفذ على الخادم.

قائمة المراجعة تعرض المادة والإصدار والمؤلف والرافع والحجم وتاريخ التقديم ونتيجة الفحص وحالة الحقوق. شاشة القرار تتيح معاينة آمنة، قبولاً، طلب تعديل بسبب واضح، أو رفضاً. لا تستخدم جدولاً عريضاً لا يمكن تشغيله من الهاتف.

القبول يتطلب فحصاً ناجحاً، ميتاداتا مكتملة، مراجعة أصل المحتوى والإذن، ومراجعة الملاءمة والوضوح. لا يراجع المشرف نسخته التي رفعها بنفسه؛ يحتاج مراجعاً مخولاً آخر. المدير يستطيع إدارة العمل لكن لا يتجاوز شروط الفحص والحقوق.

اجعل تغيير الحالة وتعيين published_version عملية ذرية. امنع سباق مراجعين، وتكرار زر القبول، والقبول بعد حجب الوثيقة. إعادة المحاولة لا تنشئ نشراً أو إشعاراً ثانياً.

كل تعديل في PDF أو العنوان أو الوصف أو الإسناد أو الحقوق بعد النشر ينشئ إصداراً مقترحاً جديداً. تبقى النسخة المنشورة السابقة حتى اعتماد الجديدة ما لم تُحجب. لا يمكن للمساهم تبديل بايتات إصدار وافق عليه المشرف.

وسم "مساهم معتمد" يتعلق بالحساب فقط. أظهر "مراجعة تنظيمية" للعمل المعتاد. لا تستخدم "مُراجع علمياً" إلا بإجراء مستقل ومختص معروف ونطاق وتاريخ موثقين، ولا تعرضها افتراضياً.

أضف بلاغاً عن خطأ علمي، مادة غير مطابقة، ملف معطوب، بيانات شخصية، أو حقوق نشر. وفر مسار حقوق منفصلاً لصاحب الحق دون اشتراط حساب طالب، مع وسيلة تواصل وحدود إساءة استخدام. لا تعرض بيانات المبلغ للمساهم أو الجمهور.

إجراء الحجب يوقف الوثيقة وإصداراتها ومعايناتها وروابطها البديلة وظهورها في البحث، ويُسجل السبب ومن اتخذ القرار ومتى. لا تعِد نشرها بناء على نسخة جديدة دون معالجة سبب الحجب.

يستطيع المساهم سحب ملفه من الإتاحة العامة، مع الاحتفاظ الأدنى بالأثر اللازم وفق سياسة الاحتفاظ. أعط مسار اعتراض ومراجعة، لا وعداً بحذف كل أثر فوراً. الوثيقة المحجوبة بسبب أمني أو حقوقي لا تحذف فوراً أدلة التحقيق اللازمة.

أضف سجل إجراءات غير قابل للتعديل من واجهات المستخدم العادية، يظهر من غيّر ماذا ومتى دون كلمات مرور أو tokens أو بيانات خاصة زائدة. لا تدّع أنه محصن ضد مدير قاعدة البيانات نفسه.

معيار القبول: رفض النشر بلا فحص أو إذن، منع الموافقة الذاتية، مراجعتان متزامنتان، تعديل PDF منشور، بلاغ وحجب، ومنع كل طرق الوصول العام بعد الحجب. اختبر الصلاحيات على روابط المعاينة ودليل الإذن أيضاً.
```

## الأمر 7: تنزيل مناسب للانقطاع ووضع توفير البيانات

HTTP Range يسمح بطلب جزء من الملف، ويستخدمه عملاء يدعمون إيقاف التنزيل واستئنافه. نحتاج أيضاً إصداراً ثابتاً والتحقق من الردود، وليس إضافة ترويسة شكلية. [توثيق MDN لطلبات النطاق](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests).

آلية تسليم الملف بعد تحقق التطبيق تعتمد في هذا المسار على معالجة Nginx للترويسة الداخلية، ويجب اختبار إعدادها وعدم إتاحة مسار التخزين مباشرة. [توثيق Nginx وX-Accel-Redirect](https://nginx.org/en/docs/http/ngx_http_proxy_module.html).

```text
نفذ المرحلة 7: تسليم الملفات المنشورة والمعاينات من المسار الآمن، وتحسين تجربة الاتصال الضعيف.

أنشئ رابط تنزيل ثابتاً لإصدار محدد غير متغير. يتحقق Django من حالة الوثيقة والإصدار في كل طلب، ثم يسلّم Nginx الملف من موقع internal عبر X-Accel-Redirect أو آلية موثوقة مكافئة إذا اختلفت البيئة. لا تقدم الملفات من مجلد public ولا تحمّلها كاملة في ذاكرة التطبيق أو المتصفح.

راجع توثيق Nginx وبيئة النشر الفعلية. اختبر السلسلة الكاملة عبر البروكسي، لا Django dev server فقط. لا تكتب parser خاصاً لـHTTP Range إذا كانت طبقة التسليم الموثوقة تتكفل به.

ادعم HEAD وGET وRange وIf-Range وETag ثابتاً لكل إصدار، وContent-Length وContent-Range وContent-Type الصحيح. تحقق من 206 للنطاق الصحيح و416 للنطاق خارج الحدود ومن اختلاف سلوك If-Range عند تغير المدقق. اختبر تطابق البايتات بعد إعادة التجميع.

احمِ هذه المسارات كلها بنفس قواعد الظهور، بما فيها HEAD وطلبات النطاق وروابط الصور والمعاينات. لا تجعل التخمين أو ترويسة X-Accel-Redirect مقدمة من المستخدم وسيلة للوصول لملف آخر. الموقع الداخلي لا يفتح بطلب مباشر.

في الإطلاق الأول استخدم Cache-Control: no-store لردود الملفات والمعاينات المحكومة بالحجب، وتحقق من الحالة على كل طلب HTTP جديد. هذا لا يمنع الطالب من حفظ التنزيل صراحة إلى هاتفه. استخدم caching طويل العمر للـstatic assets ذات البصمة فقط. إن أضفت CDN لاحقاً فلابد من سياسة إبطال مختبرة؛ لا تخزن المسودات أو الحسابات أو أدلة الحقوق فيه.

اعرض حجم التنزيل الفعلي وعدد الصفحات والعام والإصدار قبل الزر. استخدم رابطاً عادياً مع Content-Disposition مناسب واسم عربي آمن؛ لا تستخدم fetch ثم Blob لتنزيل PDF كله في RAM.

المعاينة لا تحمل عند فتح صفحة التفاصيل. عند طلبها يعرض الخادم صورة صفحة واحدة مع أزرار السابق والتالي، لثلاث صفحات أولى مبدئياً. لا يحمل PDF.js أو PDF الكامل ضمنياً. إذا لم تتوفر معاينة فالتنزيل يبقى متاحاً ولا يظهر محتوى متخيل.

أضف وضع توفير بيانات ظاهر في الإعدادات، يوقف الوسائط الاختيارية والتحميل المسبق وأي إعلانات مستقبلية وفق إعداد المشروع. الواجهة خفيفة افتراضياً حتى إن لم يدعم المتصفح Save-Data أو لم يحفظ التفضيل. لا تتعرف إلى وضع الهاتف من اسمه التجاري.

يمكن توفير نسخة مضغوطة فقط بعد إنشاء مشتق حقيقي، ومقارنة الحجم وفحص الوضوح وتوثيق صلته بالإصدار. لا تجعل الضغط سبباً لمحو ملكية المؤلف أو طمس المعادلات. النسخة الأصلية الموافق على نشرها تبقى متاحة؛ لا تعد بنسبة ضغط ثابتة لكل PDF.

لا تضف Service Worker في هذه النسخة. الدراسة دون اتصال تتم بتنزيل PDF إلى الهاتف. وضح الفرق بين المفضلة والتنزيل، ولا تدّع أن الموقع يعمل بالكامل offline أو يستطيع محو نسخ سبق للطلاب تنزيلها.

معيار القبول: تنزيل بلا حساب وبلا JavaScript، استجابة نطاق صحيحة عبر Nginx، قطع اتصال ثم طلب الباقي والتحقق من SHA-256، وحجب إصدار يمنع طلبه الجديد ومعاينته. وثق أن إيقاف اتصال جارٍ ونسخ محلية سابقة ليس مضموناً بإجراء الحجب وحده.
```

## الأمر 8: مساعدة الطلاب وإدارة نقص المحتوى

```text
نفذ المرحلة 8: المفضلة وطلبات المحتوى ومساحات الطالب والمساهم والمشرف، دون تحويل الموقع إلى شبكة اجتماعية.

أضف مفضلة مواد وملفات لصاحب الحساب في قاعدة البيانات. إضافة المفضلة وإزالتها تعملان بنماذج POST مع CSRF وبدون JavaScript. امنع التكرار والتعديل على مفضلة غيره. عند حجب ملف محفوظ تظهر حالة عدم التوفر دون كشف سبب خاص أو بيانات محجوبة.

أضف طلب مادة ناقصة مرتبطاً بمادة وعام وفصل ونوع محتوى. اعرض الطلب القائم قبل إنشاء طلب مماثل، مع "أحتاجها أيضاً" مرة واحدة لكل حساب. حالات الطلب: مفتوح، قيد المتابعة، متوفر، مغلق بسبب واضح.

لا تغلق الطلب تلقائياً لمجرد رفع ملف؛ يربط المشرف الطلب بملف منشور ملائم. أظهر حالة الطلب للطالب، مع إشعارات داخل الحساب للقرارات الضرورية فقط. لا تنفذ push أو polling مستمراً أو إرسال بريد جماعياً افتراضياً.

مساحة المساهم تعرض ملفاته وإصداراتها وحالات الفحص والمراجعة وأسباب التعديل، وتسمح ببدء تحديث جديد ضمن نطاقه. يظهر اسمه العلني ومساهماته المنشورة فقط بموافقته، دون بريد أو صلاحيات داخلية.

لوحة المشرف والمدير تعرض المواد التي لا تحتوي ملفات، والطلبات الأكثر تكراراً، والملفات القديمة حسب العام، والمهام المتعطلة، وعدد الملفات المعتمدة لكل مادة. المؤشرات مستخرجة من بيانات فعلية وليست أرقاماً لملء التصميم.

أضف زر مشاركة بالرابط العادي. Web Share ونسخ الحافظة تحسين اختياري؛ إذا لم يدعمهما المتصفح، اعرض رابطاً نصياً قابلاً للتحديد. لا تحمل SDK لتطبيق اجتماعي.

لا تعرض نجوم تقييم أو أعداد "طلاب تمت مساعدتهم" بلا تعريف وبيانات. إذا أضفت عداداً فسمه بدقة، مثل "طلبات تنزيل"، ولا تساوِ بين بدء الطلب وإكمال التنزيل أو بين الطلب وعدد الأشخاص.

معيار القبول: طالب يطلب مادة، مساهم يرفع، مشرف يعتمد ويربط الملف بالطلب، ثم الطالب يجده ويحفظه وينزله. تعمل الرحلة ضمن الأدوار وبلا JavaScript، مع اختبارات المفضلة المكررة والطلب المكرر والوصول غير المصرح.
```

## الأمر 9: حقوق المحتوى والخصوصية وصفحات الثقة

```text
نفذ المرحلة 9: آليات الحقوق والخصوصية ونصوص أصلية، لا شروط منسوخة من منافس.

أكمل تسجيل الأساس الذي يجيز النشر لكل إصدار: عمل أصلي للمساهم يملك حقوقه، إذن صريح موثق من صاحب الحق، أو ترخيص مفتوح بشروطه وإسناده. "اشتريته من مكتبة" و"وجدته على تلغرام" ليسا خيار موافقة تلقائية.

احفظ أدلة الإذن في مساحة خاصة لا تظهر في الفهرس أو المعاينات أو سجلات عامة. سجل مصدرها وتاريخها ونطاقها: العرض والتنزيل والمشتقات التقنية والإعلانات عند انطباقها. إقرار المساهم وحده لا يحسم نزاع ملكية.

جهز مسودة عربية لاتفاق المساهمة تمنح المنصة إذناً غير حصري للنشر والعرض والتنزيل المجاني والمعالجة التقنية اللازمة، دون الادعاء بامتلاك عمل الطالب. عالج دعم المنصة بالإعلانات بشفافية، ولا تفرض ترخيص Creative Commons على شخص لا يملك حق منحه. راجع القيود مثل NC أو ND بشرياً قبل الإعلانات أو التعديل، ولا تفترض أن مجانية التنزيل تحسمها.

جهز صفحات عن المبادرة والتواصل وشروط الاستخدام والخصوصية وسياسة المحتوى وطلب الإزالة والاعتراض. وضح استقلال المشروع عن الجامعة ما لم توجد شراكة موثقة. لا تستخدم ختم جامعة أو شهادة اعتماد وهمية.

هذه مسودات تحتاج مراجعة مالك المشروع ومختص بحسب بلد التشغيل والجمهور قبل الإطلاق. ضع هوية المشغل ووسيلة التواصل والبلد وفترات الاحتفاظ غير المحسومة في OPEN_QUESTIONS. لا تخترع بيانات شركة أو عنواناً قانونياً لإكمال الصفحة.

اجمع الحد الأدنى من البيانات. البريد خاص، الاسم العلني اختياري، ولا أرقام هواتف أو هويات أو تتبع مواقع دقيقة. وفر تغيير البيانات وطلب حذف الحساب، وافصل حذف الحساب عن حقوق المحتوى والاحتفاظ الضروري بسجلات النزاعات.

نفذ سياسة احتفاظ قابلة للضبط للملفات المؤقتة والمسودات المهجورة والسجلات والبلاغات والنسخ الاحتياطية. وثق كيف تطبق أوامر الحذف والحجب مجدداً عند استرجاع نسخة احتياطية، حتى لا تعيد نشر ملف سبق سحبه.

نقّح السجلات من كلمات المرور والروابط السرية وأدلة الإذن، وقيد الوصول والتصدير. لا تضف analytics خارجية أو cookie banner شكلياً بلا مراجعة ما يتم تخزينه فعلاً. كوكيز الجلسة والموافقة لها وظائف مختلفة؛ حدد المعالجة والمتطلبات الفعلية مع مراجعة قانونية عند اللزوم.

امنع نشر ملفات فيها أرقام طلاب أو درجات أو بيانات خاصة قبل معالجتها بإذن ومراجعة. لا تسمح بكتب تجارية مصورة أو تسريبات امتحانات جارية أو أعمال يقدمها الطالب باسم غيره. وسم "تعليمي" لا يتجاوز سياسة الحقوق.

معيار القبول: لا نشر بلا أساس حقوق موثق، نموذج اعتراض يصل لطابور حقيقي، عدم تسرب الإذن أو البريد، ومسار حذف وسحب محتوى قابل للاختبار. تبقى المسائل القانونية غير المحسومة عوائق إطلاق معلنة، لا ملاحظات منسية.
```

## الأمر 10: الظهور في البحث والقياس والإعلانات المؤجلة

AdSense يتطلب الالتزام بسياساته ومحتوى مناسباً، ولا يضمن قبول الموقع أو دخله. سياسات المواضع تحذر من إعلانات قد يخلطها المستخدم بأزرار التنزيل، ومن تشجيع النقر. [شروط الأهلية](https://support.google.com/adsense/answer/9724?hl=en)، [مواضع الإعلانات](https://support.google.com/adsense/answer/1346295?hl=en).

```text
نفذ المرحلة 10: SEO أساسي وقياس محدود وبنية إعلانات معطلة، دون تفعيل خدمات خارجية.

أضف عناوين ووصفاً أصلياً وصفحات مواد مفيدة للطالب، وروابط canonical للصفحات العامة الصالحة، وsitemap للمنشور فقط. لا تنشئ آلاف صفحات فارغة أو نصوص AI للحشو. لا تختلق schema للمراجعات أو التقييمات.

امنع فهرسة الحسابات والرفع والإدارة والبحث الداخلي والفلاتر المكررة والمسودات. الحماية تكون بالصلاحيات أولاً؛ robots.txt وnoindex ليسا وسيلة حماية لملف خاص. المسارات القديمة الصحيحة لها redirect مناسب، والمفقودة لا تعيد 200 زائفة.

أضف قياساً إجمالياً محدوداً للمواد المطلوبة ونتائج البحث الخالية وأخطاء الرفع والمعالجة ومحاولات التنزيل. لا تخزن كل نص بحث خام إلى الأبد؛ قد يحتوي معلومات شخصية. استخدم تجميعاً أو تنقيحاً واحتفاظاً قصيراً وفق السياسة المعتمدة، ولا تستخدم fingerprinting.

طلبات HEAD وRange وإعادة المحاولة لا تساوي مستخدمين جدداً أو تنزيلات مكتملة. عرّف كل مؤشر ومحدوديته في لوحة الإدارة. جمع مؤشرات الأداء الميدانية إن أضيف يكون صغيراً واختيارياً بحسب سياسة الخصوصية، ويتجاهل المتصفحات التي لا تدعم API القياس دون تعطيلها.

أنشئ مفتاح ADS_ENABLED=false افتراضياً، ومكوّن مكان إعلان قابل للتشغيل لاحقاً دون تغيير جوهر الصفحة. عند التعطيل لا تحمل أي script أو اتصال إعلان أو مساحة فارغة ضخمة.

عند التفعيل المستقبلي: موضع محدود منفصل بوضوح عن التنزيل والتنقل، مساحة مستقرة لا تحرك المحتوى، لا popups أو interstitials أو عدّاد انتظار أو نقر مقابل تنزيل. لا تقل "اضغط الإعلان لتدعمنا"، ولا ترسل نقرات اختبار إلى إعلان حي.

لا تعرض إعلانات في الإدارة أو الحساب أو صفحات الأخطاء أو المواد قيد نزاع. إذا فشل script الإعلان أو رفض الطالب موافقة مطلوبة تبقى الوظائف الأساسية متاحة. لا تفترض أن non-personalized ads تلغي كل متطلبات الموافقة.

جهز checklist قبل تشغيل AdSense: مراجعة شروط Google الحالية، أهلية بلد المشغل وبياناته ووسيلة الدفع الفعلية، قبول الحساب والموقع، حقوق المحتوى الممول بالإعلان، الخصوصية والموافقة عند لزومها، والوصول من سوريا وتجربة الهاتف الضعيف. لا تزعم أن وجود صاحب المشروع في بلد آخر يضمن عرض الإعلانات أو الأرباح من الزوار السوريين.

لا تنشئ ads.txt بمعرف مختلق أو حساب إعلانات حقيقياً. ضع التفعيل في OPEN_QUESTIONS حتى أوافق وتتوفر البيانات. استخرج تكاليف التخزين ونقل الملفات من الاستخدام، لكن لا تخترع أسعاراً أو عائداً لكل ألف زيارة.

معيار القبول: sitemap نظيف، عناوين غير مكررة، صفر اتصالات لطرف إعلان عند التعطيل، استمرار التنزيل مع حظر scripts خارجية، ومؤشرات معرفة بدقة. الإعلانات تبقى معطلة عند نهاية المرحلة.
```

قبل تفعيل أي خدمة، أعد التحقق من قيود الدول وشروط الناشر والدفع وقتها. لا نعتمد معلومات قديمة عن سوريا ولا نفترض إتاحة الخدمة من غياب اسم دولة في قائمة واحدة. [قيود دول AdSense](https://support.google.com/adsense/answer/6167308?hl=en-GB)، [سياسات البرنامج](https://support.google.com/adsense/answer/48182?hl=en).

## الأمر 11: اختبارات واقعية وتدقيق قبل الإطلاق

```text
نفذ المرحلة 11: تدقيق شامل وإصلاح العيوب، لا إضافة ميزات جديدة. ابدأ باختبارات المراحل السابقة ثم أكمل مصفوفة التحقق.

اختبارات المنطق: تطبيع البحث العربي، العلاقات، قيود الأدوار والنطاقات، انتقالات الفحص والمراجعة، الإصدارات الثابتة، الحجب، الدعوات، المفضلة، وطلبات المحتوى. اربط REQ IDs بأسماء الاختبارات أو أدلة التحقق.

اختبارات التكامل: PostgreSQL حقيقية مع migrations، تخزين خاص، worker وRedis وفاحص فعلي في بيئة آمنة، وبريد اختبار. لا تستبدل كل هذه الخدمات بـmocks ثم تصف تكامل الإنتاج بأنه مجرب. يمكن استخدام doubles لاختبارات وحدات محددة مع تسمية واضحة.

رحلة E2E: مدير يدعو مساهماً، المساهم يقبل ويرفع PDF من إنشائنا، المعالجة تنجح، مشرف آخر يعتمده، زائر يجده وينزله، طالب يطلب تحديثاً، مساهم يقترح إصداراً جديداً، ثم حجب يمنع النسخ والمعاينات العامة. اختبر فشل كل انتقال مهم.

الأمان: IDOR وتغيير المعرفات، تجاوز نطاق الكلية، رفع الامتيازات، الموافقة الذاتية، CSRF، XSS في العنوان والوصف وأسماء الملفات، redirects غير موثوقة، تجاوز الرفع، path traversal، المسودات عبر cache، وتجاوز الحجب عبر HEAD أو Range أو رابط قديم. لا تضف جلب ملفات من URL خارجي لأنه يفتح نطاق SSRF غير مطلوب.

اختبر حفظ حالة النماذج بعد الفشل دون حفظ كلمة مرور، والإرسال المكرر، وسحب صلاحية أثناء الجلسة، وتوقف worker، وضياع مهمة طابور، وقلة مساحة القرص، وانقطاع قاعدة البيانات، والبريد المتعطل. اختبر أن الفشل الأمني لا يسمح بالنشر.

الوصول والتصميم: Playwright بلقطات الشاشات المحددة، JavaScript معطل، التنقل بلوحة المفاتيح، ترتيب التركيز وعودته بعد النوافذ، قارئ شاشة عند توفره، تكبير 200%، تباين WCAG AA، RTL مع أسماء طويلة، وعدم تغطية لوحة المفاتيح للأزرار على الموبايل.

الأداء: تحقق آلي من ميزانيات 150 KiB للتحميل الأولي و35 KiB لـJS و30 KiB لـCSS وصفر PDF/معاينات تلقائية. استخدم build وإعداد إنتاج فعليين، تشغيلات cold cache متكررة، ونموذجي الشبكة المحددين في الدليل، وسجل حجم النقل وعدد الطلبات وLCP وCLS والاستجابة. لا تعتبر Lighthouse وحده شهادة أداء أو وصول.

نفذ فحص تنزيل عبر Nginx مع Range وقطع الاتصال ومقارنة البصمة. شغّل تجربة حمل محلية/تجريبية بأداة موثوقة، مثلاً 50 جلسة افتراضية تتصفح ثم 10 تنزيلات متزامنة، كنقطة بداية لا وعد سعة. سجل الجهاز والموارد وp95 والأخطاء وCPU وRAM والقرص. لا تضغط إنتاجاً حياً دون موافقة.

تحقق من N+1 واستعلامات البحث المكلفة وحدود الوقت والفهرسة. ضع rate limits تراعي الحساب والعملية ولا تحظر دفعة طلاب كاملة لمجرد مشاركة IP. لا تجعل CAPTCHA خارجية ثقيلة بوابة إجبارية لكل قراءة أو تنزيل.

إن لم تتوفر هواتف قديمة، أنشئ قائمة اختبار يدوي وسجلها "غير منفذ"، لا "ناجح بالمحاكاة". اختبر الوصول من اتصالين مختلفين داخل سوريا عندما يشارك مختبرون فعليون، بما فيه البريد والتخزين وHTTPS؛ لا تدّع نجاحاً جغرافياً من اختبار خارج سوريا.

سلّمني docs/QA_REPORT.md: النتائج الفعلية، البيئة، الأدلة واللقطات، العيوب مرتبة بالخطورة، والإصلاحات والاختبارات الجديدة. أي خلل صلاحيات أو حقوق أو تنزيل أو فقد بيانات يمنع الإطلاق. أي تجاوز ميزانية أداء يحتاج إصلاحاً أو قراراً صريحاً موثقاً، لا تعديل الأرقام بصمت.

معيار القبول: نجاح الاختبارات الحرجة المنفذة وإصلاح إخفاقاتها، وتصنيف كل متطلب إلى مختبر بدليل أو غير مختبر بسبب محدد. لا تعتبر بنداً غير مختبر ناجحاً، ولا تجتز بوابة الإطلاق مع عائق حرج أو اختبار إلزامي متبقٍ.
```

## الأمر 12: تجهيز التشغيل والإطلاق التجريبي

توصي قائمة Django للإنتاج بمراجعة إعدادات الأسرار وDEBUG والمضيفين وHTTPS والملفات والتشغيل. نستخدمها مع اختبارات المشروع، لا بديلاً عنها. [قائمة نشر Django](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).

```text
نفذ المرحلة 12: جهز حزمة تشغيل قابلة للتكرار وخطة إطلاق، ولا تنشر للعامة أو تشتري خدمة دون موافقتي.

راجع عوائق QA وOPEN_QUESTIONS أولاً. إذا بقي خلل صلاحيات أو فحص أو حقوق أو بيانات، أصلحه قبل النشر. إذا بقيت بيانات صاحب المشروع أو مراجعة قانونية أو اختبار جهاز/وصول حقيقي غير متوفرة، جهز ما يمكن واكتبها عوائق واضحة.

جهز تشغيل الإنتاج للتطبيق وPostgreSQL وRedis وworker والفاحص وNginx بوحدات قليلة مفهومة. وثق احتياجات موارد الفاحص ومعالجة PDF من القياس؛ لا تفترض أن أرخص خادم يكفي. PostgreSQL وRedis لا يكونان مكشوفين للإنترنت.

نفذ HTTPS وشهادة متجددة، DEBUG=false، allowed hosts صريحة، cookies آمنة، حماية CSRF صحيحة خلف البروكسي، وسياسة CSP متوافقة مع التطبيق دون فتح واسع غير مبرر. اختبر إرسال ترويسات البروكسي ولا تثق بها من أي مصدر. شغّل check --deploy في إعداد الإنتاج وراجع نتائجه.

شغّل الخدمات بصلاحيات محدودة، واعزل quarantine عن تقديم الملفات، واجعل Nginx يقرأ الملفات المطلوبة فقط. الأسرار خارج Git والصور المبنية والسجلات. بيئة staging منفصلة ببيانات اصطناعية ومفاتيح مختلفة، ومحجوبة بالمصادقة لا robots.txt وحده.

أنشئ نسخة احتياطية مشفرة خارج الخادم لقاعدة البيانات والملفات وأدلة الحقوق اللازمة، مع مفاتيح محمية واختبار استعادة منفصل. ملفات الإصدارات غير قابلة للاستبدال لتسهيل نسخة متسقة؛ وثق ترتيب نسخ الملفات والبيانات وتأجيل الحذف المادي حتى اكتمال النسخ.

اقترح هدفاً أولياً RPO لا يتجاوز 24 ساعة وRTO لا يتجاوز 8 ساعات، ثم اختبر ما يمكن إثباته فعلياً. هذه أهداف لا ضمانات. اختبر الاستعادة إلى بيئة فارغة، وعدّ الملفات وتحقق من بصمات عينات وإمكانية تسجيل الدخول والتنزيل وإعادة تطبيق الحجب والحذف.

وثق migrations آمنة ونسخة ما قبل التحديث وخطة rollback. رجوع كود قديم لا يعني تلقائياً رجوع schema؛ اختر تغييرات متوافقة تدريجياً عندما تكون هناك بيانات حقيقية. لا تستخدم migrations مدمرة أو تستبدل قاعدة الإنتاج ببيانات demo.

أضف مراقبة الحد الأدنى: أخطاء HTTP، latency، مساحة القرص، فشل البريد، عمر طابور المعالجة، تعطل الفاحص وتحديث توقيعاته، وصحة آخر نسخة احتياطية. اضبط تدوير السجلات وسياسة الاحتفاظ وتنبيهاً فعلياً لقناة يعتمدها صاحب المشروع، دون إرسال رسائل حقيقية قبل الموافقة.

جهز runbook يوضح: التشغيل والإيقاف، إنشاء أول مدير بأمان وMFA، دعوة مساهم، إضافة خطة ومواد، فحص ملف عالق، حجب مادة، الاستعادة، تدوير الأسرار، تحديث الحزم، وإيقاف الإعلانات أو الرفع مؤقتاً دون تعطيل القراءة السليمة.

خطة تجريبية مقترحة: سنة وفصل واحد، 5 مساهمين، و30 ملفاً أصلياً/مأذوناً تغطي المواد المختارة، ثم 30 إلى 50 طالباً لمدة أسبوعين. هذه أهداف تجربة لا بيانات فعلية. لا تدّع اكتمال تغطية مادة لمجرد وجود PDF واحد؛ يحدد المشرف ما يغطيه الملف وما ينقصه.

قس نجاح التجربة بقدرة الطالب على إيجاد ملف مناسب وتنزيله، وشكاوى السرعة والأخطاء، ونقص المحتوى، وقدرة الفريق على مراجعته وتحديثه. اجمع ملاحظات من هواتف قديمة، ولا توسع الكليات قبل معالجة مشاكل التجربة.

سلّمني RELEASE_CHECKLIST.md وRUNBOOK.md وQA_REPORT.md محدثاً، وأوامر التشغيل الدقيقة التي جربتها، وما لم يُجرّب أو يُنشر. إن طلبتُ النشر لاحقاً، استخدم البيئة المعتمدة وأعد التحقق من الإعدادات والنتيجة قبل إعلان النجاح.

معيار القبول: تشغيل بيئة اختبار بإعدادات مماثلة للإنتاج، نجاح رحلة الملف عبر البروكسي، واستعادة نسخة احتياطية إلى بيئة منفصلة بدليل. إذا تعذرت خطوة فسلّم ما أُنجز وسجل المرحلة غير مكتملة فيما يخصها. الإطلاق العام قرار منفصل بعد زوال العوائق وموافقتي، وليس نتيجة تلقائية لكتابة ملفات الإعداد.
```

## 7. ما الذي تحتاج أن تقرره أنت قبل الإطلاق؟

| القرار | ما يمكن فعله أثناء التطوير | ما يمنع الإطلاق بدونه |
|---|---|---|
| الاسم والهوية | اسم مؤقت من إعداد واحد وتصميم أصلي | مراجعة الاسم والنطاق وعدم الإيحاء بعلاقة رسمية غير موجودة |
| الجامعة والخطة | بيانات تجريبية موسومة | قائمة حقيقية معتمدة بأسماء المواد والسنوات والفصول |
| فريق المحتوى | حسابات اختبار وأدوار وصلاحيات | مساهمون فعليون ومراجع آخر للموافقة على عمل المساهم |
| الحقوق | سير عمل وإقرارات تجريبية | إذن مناسب للملفات الفعلية ومراجعة مسودات السياسات |
| التشغيل | إعداد محلي وstaging | استضافة وبريد وتخزين ونسخ احتياطية مجربة وهوية مشغل واضحة |
| الجمهور | محاكاة شبكة وشاشة | عينة اختبار داخل سوريا وعلى أجهزة قديمة فعلية |
| الإعلانات | مفتاح معطل ومكوّن مهيأ | موافقتك وأهلية وقبول وسياسات وقياس أثرها، ويمكن الإطلاق بدونها |

النتيجة المطلوبة ليست كثرة الصفحات أو المؤثرات. هي رحلة طالب بسيطة تنجح على جهازه، ومحتوى يمكن الوثوق بمصدره وتحديثه، وإدارة تستطيع تشغيل الموقع بأمان واستمرار.
